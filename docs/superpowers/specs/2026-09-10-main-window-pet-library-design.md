## 1. 背景与目标

用户的需求是一个主窗口：默认可以选系统自带的宠物；付费上传自家宠物照片定制；
支付、上传成功后等服务器生成并下发。这横跨总 spec 的 M1、M2、M3，拆成四个子项目，
每个单独走 spec → 计划 → 实现：

| # | 子项目 | 依赖 | 外部前提 |
|---|---|---|---|
| **A** | 客户端：主窗口 + 宠物库（本文） | 无 | 系统宠物素材自己生成 |
| B | 生成服务（M2 后端）：收照片 → 参考图 → 抠图合成 → 动作视频 → 质检 → 存储 → 下发 | spike 已验证 | 服务器、对象存储、可灵额度 |
| C | 客户端：定制流程（上传、下单、进度、下载入库） | A、B、D 的接口 | — |
| D | 账号与支付（M3） | B | 营业执照、商户号、域名备案 |

顺序：A → B + C（先用免支付测试订单跑通）→ D。

**A 的目标**：打开主窗口挑一只系统宠物，桌面上就换成它；以后启动直接陪伴。

**验收标准**

1. 首次启动只出现主窗口；点「带它回家」后宠物出现在桌面，主窗口保持打开。
2. 以后启动直接出现上次的宠物，主窗口不打开；托盘和宠物右键菜单都能打开主窗口。
3. 广场按分类筛选；卡片五种状态正确（带它回家 / 换它陪我 / 陪伴中 / 正在准备 / 素材缺失，见第 5 节）。
4. 换宠物、首次使用某个动作时，**两个窗口都不卡**（抠像不在平台线程上跑）。
5. 3 只系统宠物（金毛、柯基、布偶猫）× 5 个动作，全部通过素材质检后打进安装包。

## 2. 范围

**做**：`apps/aipet` 应用骨架（宠物窗 + 主窗口 + 托盘）；宠物库数据与设置；主窗口两个页面；
抠像移出平台线程；3 只系统宠物的素材生产与质检；素材生产脚本进仓库。

**不做**：定制流程（「立即定制」只弹"即将开放"）、账号、支付、服务端、
HUD 窗、气泡窗、养成数值、逐像素命中测试、开机自启与宠物大小等设置、抠像缓存的 LRU 清理、
抠像进度百分比（只转圈，不报百分比）。

## 3. 架构

### 3.1 进程、窗口、引擎

一个进程，两个 Flutter 窗口，一个托盘图标：

| 部分 | 引擎 | 职责 |
|---|---|---|
| 宠物窗 | **主引擎** | 透明、无边框、置顶、可拖。右键菜单：切换动作、打开宠物库、退出。唯一读写设置文件的一方 |
| 主窗口 | 子引擎（`desktop_multi_window` 0.3.1） | 普通有边框窗口，宠物广场 / 我的。关闭只关自己，宠物留在桌面 |
| 托盘 | 主引擎（`tray_manager`） | 打开宠物库、退出 |

**为什么宠物窗是主引擎**：`desktop_multi_window` 的每个窗口是独立 Flutter 引擎；
`window_manager` 在子窗口里要换一个修过的 fork 才能用。宠物窗离不开 `window_manager`
（透明、无边框、置顶、拖动、拦截关闭），主窗口只需要基本窗口能力，所以宠物窗在主引擎。

**插件注册**：`windows/runner/flutter_window.cpp` 里用 `DesktopMultiWindowSetWindowCreatedCallback`
给子窗口引擎调用 `RegisterPlugins`。主窗口引擎不使用 `alpha_video`。

### 3.2 两窗通信

通道 `WindowMethodChannel('aipet/pet')`，只传小消息，不传素材：

| 方向 | 方法 | 参数 / 返回 |
|---|---|---|
| 主窗口 → 宠物窗 | `getState` | 返回 `{currentPetId, adoptedPetIds, preparingPetId}` |
| 主窗口 → 宠物窗 | `adopt` | `{petId}`；宠物已在桌面上显示后才返回成功；失败返回错误码 |
| 宠物窗 → 主窗口 | `stateChanged` | 推送同 `getState` 的结构，主窗口据此刷新卡片 |

主窗口的请求 3 秒内没有回应即视为失败（见第 7 节）。`adopt` 分两步确认：
宠物窗收到后**立即**推送一次 `stateChanged`（`preparingPetId` = 该宠物），3 秒超时只看这一步；
之后宠物准备好、显示到桌面上，`adopt` 调用才返回成功。准备本身可以超过 3 秒，上限 60 秒，
超过按准备失败处理（见第 7 节）。

### 3.3 启动流程

```
启动 ─ 读 settings.json
      ├─ 没有 currentPetId（首次或全部失效）
      │     宠物窗保持隐藏；打开主窗口
      │     用户关掉主窗口且仍没选宠物 → 退出程序
      └─ 有 currentPetId
            宠物窗显示该宠物；主窗口不打开
```

### 3.4 首个实施任务：多窗口原型

`desktop_multi_window` 0.3.1 刚发布，和 Flutter 3.47 的配合没有验证过。计划第一个任务是最小原型：
透明置顶的宠物窗（主引擎，`alpha_video` 播放）+ 一个子窗口 + 双向发一条消息 + 托盘。
原型不通，在写业务代码前换方案（候选：主窗口做成宠物窗引擎里的第二个原生窗口）。

## 4. 宠物库数据

### 4.1 宠物文件夹

每只宠物一个文件夹，**系统宠物和将来的定制宠物格式完全相同**：

```
<petId>/
  pet.json
  stand.mp4 walk.mp4 sleep.mp4 lick_paw.mp4 act_cute.mp4
  cover.png          透明背景抠图，主窗口卡片封面
```

`pet.json`：

```json
{
  "schema": 1,
  "id": "builtin-gold",
  "name": "金毛",
  "species": "dog",
  "origin": "builtin",
  "blurb": "温柔的大暖男，走到哪跟到哪",
  "cover": "cover.png",
  "actions": ["stand", "walk", "sleep", "lick_paw", "act_cute"]
}
```

- `species` ∈ `dog | cat | other`，对应广场分类。
- `actions` 列出这只宠物有哪些动作；**循环还是一次性由代码决定**（总 spec 4.6：stand/walk/sleep 循环，其余一次性）。
- 视频是 M2 交付格式（总 spec 第 6 节）：960×960 或更高、24fps、纯绿背景、首尾可循环。

**位置**

| 来源 | 位置 | 读写 |
|---|---|---|
| 系统宠物 | `<程序目录>/data/flutter_assets/assets/pets/<petId>/`（Flutter 资源在 Windows 上就是普通文件，原生解码器可直接按路径读） | 只读 |
| 定制宠物（子项目 C） | `%APPDATA%/com.aipet/aipet/pets/<petId>/` | 下载写入 |

**这就是 A 和 B、C 之间的接口**：B/C 的交付物是一个上述格式的文件夹。

### 4.2 抠像缓存

`%APPDATA%/com.aipet/aipet/matte-cache/v1/<key>.aipmat`，
`key = sha256(源视频内容) 前 32 位十六进制 + "-" + 抠像管线版本`。
不用 pet_shell 的「路径哈希 + 修改时间」：程序目录可能搬家，升级后同名视频内容可能不同。
写入先写 `.staging/` 里的临时文件，校验通过后原子改名。只有用过的动作才生成缓存。

### 4.3 设置文件

`%APPDATA%/com.aipet/aipet/settings.json`：

```json
{ "schema": 1, "currentPetId": "builtin-gold", "adoptedPetIds": ["builtin-gold"] }
```

**只有宠物窗读写它**，主窗口一律通过 3.2 的通道请求——两个引擎同时写同一个文件会互相覆盖。
写入同样走临时文件 + 原子改名。「首次启动」不单独存标志，等价于没有有效的 `currentPetId`。

### 4.4 Dart 分层

沿用总 spec 4.5 的目录，这次只落需要的部分：

```
apps/aipet/lib/
  main.dart                      按窗口参数决定挂载宠物窗还是主窗口
  app/pet_window/                宠物窗 UI、右键菜单
  app/main_window/               广场、我的、卡片、主题
  domain/pet.dart                Pet、PetAction、循环策略、中文名
  domain/library_state.dart      领养 / 当前宠物 / 卡片状态（纯函数）
  services/pet_library.dart      扫描系统宠物与定制宠物文件夹、解析 pet.json
  services/settings_store.dart   settings.json 读写与损坏恢复
  services/matte_cache.dart      缓存键、按需抠像
  services/window_bridge.dart    3.2 的通道两端
```

`pet_shell` 的 `actions.dart` 与切换、一次性动作回待机的逻辑搬进 `domain/` 和宠物窗，
`pet_shell` 保留为开发验证工具。状态管理用 Riverpod（总 spec 4.5）。

## 5. 主窗口界面

**窗口**：竖长，约 420×740 逻辑像素，有边框，可最小化、关闭。标题「aipet」。

**配色（我们自己的暖色调，不照搬竞品粉色）**

| 用途 | 色值 |
|---|---|
| 页面底色 | `#FFF8F0` 奶油白 |
| 卡片底色 | `#FFFFFF` |
| 主强调（按钮、选中标签） | `#F08A3C` 暖橙 |
| 强调浅底（标签底、横幅底） | `#FDEBD9` |
| 主文字 | `#3D2B1F` |
| 次文字 | `#8A6E5A` |

**宠物广场（默认页）**

- 顶部横幅：「定制专属宠物」+「上传您的爱宠照片，生成桌面伙伴」+「立即定制」按钮 → 弹窗「即将开放，敬请期待」。
- 分类标签：全部 / 狗狗 / 猫猫 / 其他小宠。空分类显示「这里还没有小伙伴」。
- 两列卡片：封面、名字、一句简介。卡片五种状态：

| 状态 | 条件 | 显示 |
|---|---|---|
| 未领养 | 不在 `adoptedPetIds` | 按钮「带它回家」 |
| 已领养未陪伴 | 在 `adoptedPetIds`，不是 `currentPetId` | 按钮「换它陪我」 |
| 陪伴中 | 是 `currentPetId` | 标记「陪伴中」，按钮不可点 |
| 准备中 | 是 `preparingPetId` | 按钮转圈 +「正在准备…」，不可点 |
| 素材缺失 | 文件夹不完整 | 灰显「素材缺失」，不可点 |

**我的**：已领养宠物的卡片（同上）；空状态「还没有领养小伙伴，去广场看看吧」；底部「退出程序」。

**底部导航**：宠物广场 / 我的。

## 6. 抠像移出平台线程

**问题**：同一进程里所有窗口共用一个平台线程。`pet_matte_prepare` 在平台线程上同步执行
（release 约 2.6 秒 / 动作，HANDOFF 待办 2），换宠物或首次用某个动作时两个窗口一起卡住，
超过 5 秒会被 Windows 标成"无响应"。

**做法**（只改 `packages/alpha_video` 的原生侧，Dart 接口 `AlphaVideo.prepare(...)` 不变，
本来就返回 `Future`）：

- 收到 `prepare` 调用后，把 `MethodResult` 存起来，在工作线程上执行 `pet_matte_prepare`。
- 完成后通过插件自有的消息窗口 `PostMessage` 回到平台线程，再回复 `MethodResult`
  （Flutter Windows 的 `MethodResult` 只能在平台线程上回复）。
- 同一个目标文件的并发 `prepare` 合并成一个任务，全部调用方拿同一个结果。
- 插件析构时等待在途任务结束，不留悬空线程（HANDOFF 坑 5：定时等待用带谓词的 `cv.wait_for`）。

**界面**：换宠物时宠物窗继续显示旧宠物，新宠物的 `stand` 准备好后再无缝切换；
主窗口对应卡片显示「正在准备…」。

## 7. 出错处理

| 情况 | 处理 |
|---|---|
| 系统宠物文件缺失或损坏 | 卡片「素材缺失」，不可领养；当前宠物素材缺失 → 换成另一只已领养宠物，没有就按首次启动处理 |
| 抠像失败 | 宠物窗显示一句简短提示，右键菜单照常；缓存不落盘（临时文件 + 原子改名） |
| `settings.json` 解析失败 | 改名为 `settings.json.bad` 保留，按首次启动处理 |
| 主窗口请求 3 秒无响应 | 卡片提示「切换失败，请重试」，不改界面状态 |
| `adopt` 准备失败 | 宠物窗保持旧宠物，推送 `stateChanged`（`preparingPetId` 清空），主窗口提示失败原因 |

## 8. 测试

- **单元测试（纯 Dart）**：`pet.json` 解析与校验；领养 / 当前 / 准备中 / 缺失的卡片状态计算；
  设置文件读写与损坏恢复；缓存键；循环策略与中文名（沿用 pet_shell 的 26 个测试并扩展）。
- **Widget 测试**：分类筛选；五种卡片状态；「即将开放」弹窗；「我的」空状态。
- **原生测试（GoogleTest）**：prepare 异步化——并发同目标合并、完成回调在平台线程、析构等待在途任务。
- **真机验证**：多窗口原型；首次启动 → 领养 → 宠物出现；重启直接出现；托盘与右键打开宠物库；
  领养时两个窗口不卡（主窗口转圈时仍能滚动）。用 DPI 感知的点击脚本
  （物理像素坐标，点击前校验落点像素）；**每次动鼠标前先告知用户**。

## 9. 系统宠物的素材生产

脚本从 spike 的临时目录搬进仓库 `tools/petgen/`（Python），它同时是子项目 B 服务端管线的雏形。

**流程**（每只宠物）：

1. 源照片：`kling-v3` 文生图，写明品种与花纹。无参考图——宠物是虚构的，不涉及真实动物的肖像或照片版权。
2. 姿态参考图：`kling-v3` 图片生成 + `image_reference: subject`（以源照片为主体），浅灰底；
   站 / 走 16:9，趴 21:9（1:1 和 16:9 下长条身体的尾巴会碰画框）。
3. 参考图门槛：
   - 碰边：**用分割出的 alpha** 判断主体是否碰到原图边缘（留 2 像素）。不能按颜色猜——中灰背景会被误判成前景。
   - 合成：BiRefNet-lite + alpha matting → 精确 `#00FF00`，居中到 1024 方图。
   - 抠像打分：逐像素复刻 pet_matte 键控，漂浮半透明像素 < 911（竞品参考帧的值）。
4. 动作视频：`kling-v3` std 5s，`image = image_tail = 参考图`。
   stand / lick_paw / act_cute 用站姿图，walk 用走姿图（站姿图做 walk 会变成「站—走—站」），sleep 用趴姿图。
5. 视频质检：960×960 / 24fps / 121 帧；接缝（末→首）PSNR 不低于片内最大相邻帧跳变；
   首末帧抠像打分 < 911。
6. 产出 `cover.png`（站姿图的 alpha 抠图）与 `pet.json`。

**预算**：15 个视频 × 3 单位 = 45 视频单位（剩 79，余量留给重试）；图片每张 8 单位（剩约 850）。

## 10. 风险

| 风险 | 对策 |
|---|---|
| `desktop_multi_window` 与 Flutter 3.47 不兼容 | 3.4 原型先行，不通就换方案 |
| prepare 异步化碰到 Flutter Windows 线程约束 | 只在平台线程回复 `MethodResult`；原生测试覆盖 |
| 猫的管线未验证 | 布偶猫素材最先生产；质检不过就换品种 |
| 可灵生成内容的商用条款 | 发布前确认生成素材可以商用分发 |
| 视频额度不够重试 | 质检不过先调提示词；额度用尽前停下来报告 |

## 11. 与后续子项目的接口

- **交付格式**：第 4.1 节的宠物文件夹。B 生成、C 下载到 `%APPDATA%/com.aipet/aipet/pets/<petId>/`，
  主窗口「我的」自动出现（`origin: "custom"`）。
- **定制入口**：广场顶部横幅的「立即定制」，C 接手后替换掉「即将开放」弹窗。
