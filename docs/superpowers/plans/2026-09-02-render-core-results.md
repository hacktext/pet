# Task 11 实测数据（透明置顶窗端到端验证）

记录时间：2026-09-03。测试机：16 逻辑核，主屏 2560x1600 @ 150% DPI 缩放。

素材：`walk-walk.mp4`（1440x1440，121 帧，24fps，开发期素材，未入库）。
`flutter build windows --release` 产物 `pet_shell.exe`，`targetEdge=720`。

## 磁盘占用

`.aipmat` 文件大小：**41,605,826 字节（约 39.7 MiB / 41.6 MB）**。

## 抠像耗时（prepare()）

`AlphaVideo.prepare()` 从调用到返回：**约 2.6 秒**（16:01:26.321 → 16:01:28.935，
code=0）。这是 Release 优化构建下的数字；早前 Debug 构建下同一素材的测量约 9.7 秒，
两者差异符合 Release 优化预期，不是矛盾。

## 启动到首帧可见的挂钟时间

从进程创建（`Get-Process` 报告的 `StartTime`）到 Dart 侧记录的
"first frame with controller painted"（`WidgetsBinding.addPostFrameCallback`，
即 `setState(() => _controller = c)` 之后的下一次真实渲染帧）：

- 进程 StartTime：16:01:24.3717
- 首帧绘制：16:01:28.9609
- **挂钟耗时：约 4.6 秒**（其中约 2.6 秒是 `prepare()` 抠像，其余是引擎/窗口初始化
  + `open()`/`play()` 调用开销）

## 稳态 CPU 占用

播放循环中连续采样 40.14 秒挂钟时间（每 5 秒一次 `Get-Process`）：

- 起点累计 CPU 时间 27.531s → 终点 29.8125s，增量 1.609s
- **CPU% = 1.609s / 40.14s / 16 核 × 100% ≈ 0.25%**（与任务管理器默认口径一致，
  即相对全部逻辑核的占用）
- 折算到单核口径（1 核 = 100%）约为 4.0%
- 两种口径下都远在个位数百分比以内，验收判据 5 通过

## 内存占用（working set）

采样窗口内（8 个采样点，5 秒间隔）working set 稳定在 **164.3–164.5 MB**，无增长趋势
（未观察到播放期间的内存泄漏迹象；40 秒窗口较短，不能排除更长时间尺度的缓慢增长，
仅报告观察到的数据）。

## 对 Plan B 窗口与缓存决策的参考

- `.aipmat` ~41.6MB / 121 帧、720 长边，对应约 24 帧/秒场景下几秒钟量级的素材；若
  Plan B 支持多组动作（`act_cute`/`feed`/`play`/`run`/... 每个约 4-10MB 源视频），
  单宠物多动作缓存总量会到几百 MB 量级，LRU/缓存目录设计需要按这个量级规划，而不是
  单文件几十 KB 的量级。
- 稳态 CPU 0.25%（全核口径）说明当前 `PixelBufferTexture` + CPU 拷贝路径在单窗口
  单动作播放下开销很小，Plan A 后续「D3D11 GpuSurfaceTexture 升级」一节里提到的
  "等 Task 11 实测数据出来再决定要不要做" 的决策依据是：**在当前测得的规模下没有
  紧迫性**；这个结论只覆盖单窗口场景，Plan B 的多窗（HUD/气泡/托盘）场景应重新测量，
  因为 CPU 拷贝开销会随窗口数線性增长，而 GPU 纹理共享不会。
- 启动到首帧约 4.6 秒里 2.6 秒花在 `prepare()`（抠像编码），是全流程里最大的单项
  耗时来源。Plan B 的缓存目录/cacheKey 设计的价值在这里最直接：素材一旦生成过
  `.aipmat` 并缓存命中，这 2.6 秒就可以省掉，只剩 `open()`+`play()` 的约 10ms 级
  开销。
